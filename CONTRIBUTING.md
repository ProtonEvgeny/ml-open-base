# Как контрибьютить

ML Open Base — открытый проект, и мы рады исправлениям, переводам и новым материалам.
Все изменения проходят через ветки и pull request: ветка `main` защищена, прямые пуши в
неё закрыты, в том числе для мейнтейнеров.

## Быстрый чек-лист

- [ ] Ветка создана от свежего `main` и названа по схеме `<type>/<kebab-slug>`.
- [ ] Коммиты оформлены по Conventional Commits на английском.
- [ ] `npm run build` и `npm run doctor` проходят без новых ошибок.
- [ ] PR сфокусирован на одной задаче и содержит описание и способ проверки.
- [ ] В PR нет сгенерированных файлов, секретов и посторонних правок.
- [ ] После ревью выполнен squash-мердж, ветка удалена.

## Что можно добавить

- новые материалы и разделы базы знаний;
- исправления фактических ошибок, опечаток и битых ссылок;
- переводы на английский;
- улучшения сайта, скриптов и конфигурации.

## Перед началом

- Для крупных изменений — новой рубрики, перестройки разделов, смены стека или
  формата контента — сначала откройте issue и согласуйте объём.
- Мелкие правки можно сразу оформлять pull request.
- Убедитесь, что установлен Node.js >= 22.19.0:

  ```bash
  nvm use
  npm install
  ```

- Если вы агент, дополнительно прочитайте [AGENTS.md](AGENTS.md). Для агентов
  действуют те же git-правила, что и для людей.

## Ветки

В репозитории одна долгоживущая ветка — `main`. Она защищена и обновляется только
через pull request.

- Создавайте короткоживущую ветку от актуального `main`.
- Не заводите долгоживущие ветки `develop`, `release` и подобные.
- После мерджа удаляйте ветку.
- Название ветки: `<type>/<краткий-слаг>`.
- Используйте только ASCII, нижний регистр и `kebab-case`; без имён, дат и `wip`.
- Ориентир — 2–5 слов. Если есть issue, можно добавить его номер.

| Тип        | Когда использовать                                      |
| ---------- | ------------------------------------------------------- |
| `content`  | новый или изменённый материал базы знаний               |
| `docs`     | README, AGENTS, CONTRIBUTING, конфигурация документации |
| `fix`      | исправление ошибки, битой ссылки, опечатки              |
| `feat`     | новая функциональность сайта или скриптов               |
| `chore`    | зависимости, версия Node, служебные файлы               |
| `ci`       | GitHub Actions и автоматизация                          |
| `refactor` | переработка без изменения поведения                     |

Примеры:

```text
content/transformers-basics
fix/broken-attention-link
docs/git-workflow
ci/build-and-doctor
chore/node-22
content/42-tokenization
```

Если `main` ушёл вперёд, перебазируйте свою ветку на него:

```bash
git fetch origin
git rebase origin/main
```

## Коммиты

Используйте [Conventional Commits](https://www.conventionalcommits.org/) на английском:

```text
<type>(<scope>): <summary>
```

- `type` — из таблицы выше;
- `scope` — необязательный, но полезный: раздел или область (`nlp`, `site`, `deps`, `ci`);
- `summary` — повелительное наклонение, строчная буква, без точки в конце;
- вся первая строка — не длиннее 72 символов;
- тело коммита объясняет **зачем** сделано изменение, а не пересказывает diff;
- в футере укажите связанные issue: `Closes #42`; breaking changes — через
  `BREAKING CHANGE: ...`.

Примеры:

```text
content(nlp): add tokenization overview
fix(docs): correct attention formula link
docs(contributing): describe branch and commit rules
chore(deps): bump blume to 2.2.7
ci: run build and doctor on pull requests
```

Один коммит — одна логическая правка. Не смешивайте контент, форматирование и
инфраструктуру в одном коммите. Внутри ветки промежуточные коммиты допустимы: в `main`
попадает один squash-коммит на PR.

## Pull request

- Название PR оформляется как будущий squash-коммит, то есть по Conventional Commits
  на английском. Описание PR можно писать по-русски.
- Один PR — одна логическая правка. Не добавляйте попутный рефакторинг и
  переформатирование посторонних файлов.
- Ориентир по размеру — до ~400 изменённых строк. Крупное изменение лучше разбить на
  несколько PR.
- Незаконченную работу открывайте как Draft PR.
- В описании укажите: что изменено, зачем, как проверено и связанные issue.
- Для изменений интерфейса приложите скриншоты.
- Для контента укажите статус английского перевода: обновлён или отстаёт.

Перед открытием PR локально выполните:

```bash
npm run build
npm run doctor
```

Дополнительно можно проверить собранный сайт:

```bash
npx blume audit
```

`doctor` завершается с ошибкой при error-диагностиках; предупреждения не блокируют
сборку, но новые предупреждения лучше не оставлять.

Те же шаги выполняет CI на каждый PR в `main` — workflow
[`.github/workflows/ci.yml`](.github/workflows/ci.yml), job `build-and-doctor`. Красные
проверки блокируют мердж.

## Ревью и мердж

- Внешнему контрибьютору нужен аппрув мейнтейнера.
- Пока мейнтейнер один, он может мержить свой PR после прохождения проверок.
- Автор закрывает обсуждения после исправлений.
- Мердж — только **Squash and merge**. Merge-коммиты и rebase-мердж не используем,
  чтобы история `main` оставалась линейной.
- После мерджа ветка удаляется.
- Force-push разрешён только в собственную незамердженную ветку и только через
  `--force-with-lease`. В `main` force-push запрещён.
- Конфликты решайте ребейзом на `main`, а не мерджем `main` в ветку.

## Правила для контента

- Материалы на языке по умолчанию лежат в `docs/`, переводы — в `docs/en/`.
- У новой страницы должны быть `title` и `description` во frontmatter.
- Frontmatter — валидный YAML. Значения с `: ` берите в кавычки.
- В `.mdx` символы `{` и `<` являются синтаксисом. Экранируйте их, если они нужны как
  текст.
- Ссылки делайте относительными; не ссылайтесь на сгенерированные файлы.
- Не переформатируйте файлы, которые не относятся к задаче.
- Крупную перестройку структуры разделов сначала согласуйте в issue.

## Чего не делать

- Пушить напрямую в `main`.
- Коммитить `.blume/`, `dist/`, `node_modules/`.
- Коммитить секреты, токены и локальные env-файлы (`.env*`).
- Смешивать в одном PR контент, инфраструктуру и форматирование.
- Редактировать `package-lock.json` вручную.
- Менять версию Node без обсуждения.
- Оставлять после мерджа неиспользуемые ветки.
